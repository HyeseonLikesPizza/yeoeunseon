# 경쟁 상태(Race Condition)

> [!summary]
> **문제:** 여러 스레드의 실행 순서에 따라 결과가 달라진다.
>
> ```text
> 같은 일반 변수 + 겹칠 수 있는 접근 + 하나 이상 쓰기 + 동기화 없음
>                         ↓
>                   Data Race → C++에서는 UB
> ```
>
> **해결:** 공유를 줄이고, 복합 작업은 `mutex`, 단순한 값 하나는 `atomic`으로 보호한다.
>
> ```text
> mutex         여러 코드와 데이터를 한 번에 한 스레드만 처리
> atomic        변수 하나의 연산을 쪼개지 않게 처리
> lock-free     저지연·동시성 자료구조에서 확인할 진행 보장
> Happens-Before 동기화로 만들어지는 순서·가시성 관계
> volatile      일반 게임 코드의 스레드 동기화에는 사용하지 않음
> ```

## 왜 문제가 생길까

두 스레드가 같은 `Counter`를 증가시킨다고 해 보자.

```cpp
int Counter = 0;

void Increase()
{
    ++Counter;
}
```

`++Counter`는 한 줄이지만 실제로는 **읽기 → 증가 → 쓰기** 과정이다.

```text
Thread A: 0 읽기 → 1 계산 ─────────→ 1 쓰기
Thread B:      0 읽기 → 1 계산 ────→ 1 쓰기

기대: 2
가능한 결과의 예: 1
```

두 스레드가 같은 값을 읽고 각각 1을 쓰면 한 번의 변경이 덮어써진다. 이를 **Lost Update(갱신 손실)**라고 한다.

> [!caution]
> 위 코드는 Data Race이므로 **정의되지 않은 동작(Undefined Behavior, UB)**이다. 도식은 문제가 생기는 순서 하나를 보여줄 뿐이며 실제 결과가 반드시 1이라는 뜻은 아니다.

## Race Condition과 Data Race

| 용어 | 한 줄 의미 |
| --- | --- |
| **Race Condition** | 실행 순서에 따라 프로그램의 올바른 결과가 달라지는 문제 |
| **Data Race** | 같은 메모리에 보호 없이 충돌하는 접근이 발생한 상태 |

두 용어는 서로 구분해야 한다. Data Race는 C++에서 UB이며 Race Condition의 원인이 되는 경우가 많다. 반대로 atomic으로 Data Race를 없애도 여러 연산의 논리적 순서가 잘못되면 Race Condition은 남을 수 있다.

```cpp
std::atomic<bool> Claimed{false};

if (!Claimed.load())  // 확인
{
    Claimed.store(true); // 변경
    UseReward();
}
```

두 atomic 연산은 각각 안전하지만 **확인과 변경 전체**가 하나의 연산은 아니다. 두 스레드가 모두 `false`를 읽으면 둘 다 실행될 수 있다.

### Data Race 빠른 판별

| 동기화 없는 일반 변수 접근 | 결과 |
| --- | --- |
| 읽기 + 읽기 | 다른 쓰기가 없다면 안전 |
| 읽기 + 쓰기 | Data Race |
| 쓰기 + 쓰기 | Data Race |

## 해결 방법

### 먼저 mutex와 atomic의 차이

둘 다 여러 스레드의 충돌을 막지만 **보호하는 단위**가 다르다.

```text
mutex
┌────────────────────────────┐
│ 여러 변수와 여러 코드 줄을 보호 │
└────────────────────────────┘

atomic
┌──────────────┐
│ 변수 하나의 연산 │
└──────────────┘
```

| 구분 | `std::mutex` | `std::atomic` |
| --- | --- | --- |
| 보호 대상 | 임계 구역 안의 코드와 데이터 | atomic으로 선언한 객체의 개별 연산 |
| 적합한 작업 | 여러 줄·여러 변수를 하나로 처리 | 카운터 증가, 플래그 변경 |
| 다른 스레드 | 잠금이 풀릴 때까지 기다림 | 명시적인 mutex 없이 같은 atomic에 접근 |
| 핵심 | **구역을 잠근다** | **연산을 쪼개지 않게 한다** |

### std::mutex: 여러 작업을 하나로 보호

`mutex`는 한 번에 한 스레드만 잠긴 구역에 들어오게 한다. 이 보호 구역을 **임계 구역(Critical Section)**이라고 한다.

```cpp
std::mutex AccountMutex;
int PlayerGold = 100;
int ShopGold = 0;

void BuyItem()
{
    std::lock_guard<std::mutex> Lock(AccountMutex);

    PlayerGold -= 10;
    ShopGold += 10;
}
```

돈을 빼는 작업과 더하는 작업은 반드시 함께 끝나야 한다. mutex는 두 변수와 두 코드 줄 전체를 다른 스레드가 중간에 건드리지 못하게 한다.

`std::lock_guard`는 생성될 때 잠그고 범위를 벗어나면 자동으로 해제한다. 이런 수명 기반 자원 관리를 **RAII**라고 한다.

> [!important]
> 같은 공유 데이터를 읽거나 쓰는 모든 스레드가 **동일한 mutex**를 사용해야 한다. 한쪽만 잠그거나 서로 다른 mutex를 사용하면 보호되지 않는다.

### std::atomic: 값 하나의 연산을 보호

atomic은 변수 하나에 수행하는 특정 연산을 다른 스레드가 중간 상태로 관찰하지 못하도록 한다.

```cpp
std::atomic<int> Counter{0};

void Increase()
{
    Counter.fetch_add(1);
}
```

`fetch_add(1)`은 하나의 원자적 읽기-수정-쓰기 연산이다.

```text
일반 Counter++
읽기 → 증가 → 쓰기       중간에 다른 스레드가 끼어들 수 있음

atomic fetch_add(1)
[읽기 + 증가 + 쓰기]     하나의 원자적 연산
```

atomic은 자신에게 수행된 연산만 보호한다. atomic 앞뒤의 다른 코드까지 자동으로 하나의 임계 구역이 되는 것은 아니다.

### atomic 여러 개는 하나의 작업이 아니다

`atomic`은 '변수 하나'만 보호한다. 여러 변수를 함께 변경해 규칙을 유지해야 한다면 `mutex`로 전체 작업을 보호해야 한다.
### Lock-free는 왜 알아야 할까?

> **결론: 일반적인 게임 코드에서는 lock-free를 직접 구현할 일이 드물다.**
>
> 다만 `atomic을 사용했다 = 내부 잠금도 없고 절대 멈추지 않는다`는 뜻은 아니라는 점을 알기 위해 필요한 개념이다.

> [!summary]
> **Lock-free는 잠금을 기다리느라 전체가 멈추지 않고, 경쟁 중 적어도 하나가 계속 완료되는 구조다.**

모든 스레드가 동시에 성공한다는 뜻은 아니다. 한 스레드가 작업을 완료하는 동안 충돌한 다른 스레드는 실패하고 재시도할 수 있다.

```text
mutex
락을 가진 Thread A가 멈춤
        ↓
같은 락이 필요한 Thread B도 기다림

lock-free 알고리즘
Thread A가 멈추거나 재시도
        ↓
Thread B는 작업을 완료할 수 있음
```

`std::atomic`이라는 타입 자체가 항상 lock-free를 보장하지는 않는다. 타입과 플랫폼이 연산을 직접 지원하지 않으면 구현체가 내부 잠금을 사용할 수 있다.

```cpp
const bool bLockFree = Counter.is_lock_free();
```

다음 상황이 아니라면 보통 lock-free 여부까지 확인할 필요는 없다.

- 락을 소유한 스레드의 중단 때문에 시스템 전체 진행이 막히면 안 되는 코드
- lock-free 큐 같은 동시성 자료구조를 직접 구현할 때
- 프로파일링 결과 mutex 대기가 실제 병목으로 확인됐을 때

> [!note]
> Lock-free도 개별 스레드의 즉시 완료를 보장하지 않는다. 충돌한 스레드는 계속 재시도할 수 있다. 모든 스레드가 제한된 단계 안에 완료되는 더 강한 보장은 **Wait-free**다.

### atomic이 빠를 수도, 느릴 수도 있는 이유

단순한 카운터 하나라면 atomic은 별도의 임계 구역과 mutex 잠금·해제 과정이 없어 더 적은 작업으로 끝날 수 있다.

하지만 여러 코어가 같은 atomic을 계속 수정하면 **캐시 라인 바운싱(Cache Line Bouncing)**이 발생할 수 있다.

```text
Core A가 Counter 수정
Core A가 해당 캐시 라인의 쓰기 권한 획득
        ↓
Core B가 Counter 수정
쓰기를 위해 같은 캐시 라인의 권한을 Core B로 이동
        ↓
Core A가 다시 수정
권한을 다시 Core A로 이동
```

CPU 캐시는 데이터를 캐시 라인 단위로 관리한다. 한 코어가 값을 쓰려면 그 캐시 라인을 쓰기 가능한 상태로 가져오고, 다른 코어가 가진 같은 캐시 라인 사본을 무효화해야 한다. 여러 코어가 번갈아 쓰면 이 소유권과 데이터가 코어 사이를 계속 오가므로 비용이 커진다.

> [!important]
> 이 과정의 목적은 **Data Race를 막는 것**이 아니라, 코어마다 가진 캐시 사본이 서로 다른 값을 유지하지 않도록 하는 **캐시 일관성(Cache Coherence)**이다.
>
> 하드웨어가 캐시 일관성을 유지해도 C++의 동기화가 자동으로 생기지는 않는다. 같은 일반 변수를 여러 스레드가 보호 없이 읽고 쓰면 여전히 Data Race이며, mutex나 atomic이 필요하다.

서로 다른 변수라도 같은 캐시 라인에 들어 있으면 같은 현상이 생길 수 있다. 이를 **False Sharing(거짓 공유)**이라고 한다.

따라서 atomic은 단순 연산에서 유리할 수 있지만, 많은 스레드가 한 변수에 몰리면 병목이 될 수 있다.

## Happens-Before

> **Happens-Before는 함수나 C++ 문법이 아니라, C++ 메모리 모델이 정의하는 두 작업 사이의 순서 관계다.**
>
> **같은 mutex를 사용하면, 앞 스레드의 `unlock()` 이전 작업은 그 mutex를 다음으로 `lock()`한 스레드의 작업보다 Happens-Before가 된다.**

CPU와 컴파일러는 허용되는 범위에서 명령을 재배치할 수 있다. 따라서 한 스레드가 소스 코드에서 먼저 값을 썼다는 이유만으로 다른 스레드가 그 값을 올바르게 본다고 보장할 수는 없다.

### 어떤 코드가 재배치될 수 있을까?

프로그래머가 재배치 명령을 직접 작성하는 것이 아니다. 컴파일러와 CPU가 서로 의존하지 않는 명령의 순서를 성능을 위해 자동으로 바꿀 수 있다는 뜻이다.

```cpp
A = 1;
B = 2;
```

한 스레드에서 최종 결과가 `A == 1`, `B == 2`로 같다면 두 저장의 내부 처리 순서가 달라도 해당 스레드의 관찰 결과는 같다. 컴파일러는 이렇게 프로그램에서 관찰되는 결과를 바꾸지 않는 범위에서 최적화할 수 있다. 이를 **As-If Rule**이라고 한다.

반면 다음 코드는 두 번째 계산이 첫 번째 결과에 의존하므로 결과가 달라지게 마음대로 바꿀 수 없다.

```cpp
A = 1;
B = A + 1;
```

문제는 다른 스레드가 동기화 없이 중간 상태를 보려고 할 때다.

```cpp
Data = 42;
Ready = true;
```

작성자는 다른 스레드가 `Ready == true`를 보면 `Data == 42`도 볼 것이라고 기대할 수 있다. 하지만 일반 변수를 보호 없이 공유하면 Data Race이며, 작성 순서만으로 스레드 간 순서와 가시성이 보장되지 않는다.

> [!note]
> 모든 코드가 실제로 재배치된다는 뜻은 아니다. 컴파일러 최적화, CPU 아키텍처, 명령 사이의 의존성에 따라 달라진다. 중요한 점은 동기화 없는 코드가 특정 실행 순서를 가정해서는 안 된다는 것이다.

Happens-Before 관계가 있으면 C++는 다음을 보장한다.

1. 앞 작업이 뒤 작업보다 먼저 처리된 것으로 본다.
2. 앞 작업에서 쓴 값을 뒤 작업이 볼 수 있다.

```text
Thread A                              Thread B

mutex 잠금
Data = 42
mutex 해제  ── Happens-Before ──→    mutex 잠금
                                      Data 읽기: 42
                                      mutex 해제
```

Thread B가 같은 mutex를 성공적으로 잠갔다면, 그보다 앞선 Thread A의 잠금 해제 이전 작업 결과를 올바르게 볼 수 있다.

Happens-Before라는 함수를 직접 호출하는 것이 아니다. 다음 동기화 기능을 올바르게 사용하면 그 결과로 관계가 만들어진다.

| 사용하는 기능 | 만들어지는 보장의 예 |
| --- | --- |
| 같은 mutex의 해제와 다음 잠금 | 해제 전의 쓰기를 다음 잠금 이후에 볼 수 있음 |
| `std::thread::join()` | 작업 스레드의 완료가 `join()` 반환보다 앞섬 |
| release 저장값을 관찰한 atomic acquire 연산 | release 전의 쓰기를 acquire 이후에 볼 수 있음 |

> [!note]
> 처음에는 직접 Happens-Before 관계를 계산하려 하지 않아도 된다. 공유 데이터는 같은 mutex로 보호하고, atomic의 메모리 순서는 기본값을 사용하면 된다. 저수준 동기화를 직접 설계할 때 이 개념이 중요해진다.

## volatile

> **결론: 일반적인 C++·Unreal 게임 코드에서는 `volatile`을 직접 사용할 일이 거의 없다. 멀티스레드 동기화에는 사용하지 않는다.**

`volatile`은 메모리 접근 자체가 중요한 값임을 컴파일러에 알리는 한정자다. 일반 변수처럼 접근을 함부로 생략하거나 합치지 않도록 제한한다.

주로 다음과 같은 특수한 저수준 환경에서 사용한다.

- 임베디드·드라이버에서 하드웨어 레지스터를 읽고 쓸 때
- 신호 처리 코드에서 `volatile std::sig_atomic_t`를 사용할 때

```cpp
// 구현 환경이 제공하는 하드웨어 상태 레지스터의 예
volatile std::uint32_t* StatusRegister = GetStatusRegister();
const std::uint32_t Status = *StatusRegister;
```

하드웨어는 프로그램 코드와 무관하게 레지스터 값을 바꿀 수 있다. 따라서 컴파일러가 “값이 바뀌지 않았을 것”이라고 보고 읽기 작업을 없애면 안 된다.

하지만 `volatile`은 원자성, 상호 배제, Happens-Before를 제공하지 않는다.

```text
게임의 공유 변수·플래그       → atomic 또는 mutex
하드웨어 레지스터·특수 신호 처리 → volatile을 검토
```

```cpp
volatile bool Ready = false; // 스레드 간 Ready 플래그로 사용하면 안 됨
```

## Unreal에서의 핵심

Worker Thread에서는 `UObject`를 직접 조작하지 않고 복사된 순수 데이터만 계산한다.

1. GameThread에서 필요한 값을 복사한다.
2. Worker Thread에서 복사본으로 계산한다.
3. GameThread로 돌아와 객체 유효성을 확인하고 결과를 반영한다.

자세한 코드는 [[Async & ThreadPool]] 참고.
