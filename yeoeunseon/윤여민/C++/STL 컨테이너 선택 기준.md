# STL 컨테이너 선택 기준

> [!summary]
> **컨테이너는 종류를 다 외우기보다, 언제 쓰는지를 먼저 잡는다.**
>
> 먼저 `vector`, `unordered_map`, `unordered_set`을 기본 축으로 잡고, 정렬·앞뒤 삽입·고정 크기·특수 규칙이 필요할 때 다른 컨테이너를 붙인다.

---

## 기본 분류

| 묶음 | 컨테이너 | 핵심 질문 |
| --- | --- | --- |
| 순서대로 담는 것 | `vector`, `array`, `deque`, `list` | 순회, 인덱스, 삽입·삭제 위치 |
| key나 값으로 찾는 것 | `unordered_map`, `map`, `unordered_set`, `set` | key 검색, 존재 확인, 정렬 필요 여부 |
| 꺼내는 규칙만 정해진 것 | `stack`, `queue`, `priority_queue` | LIFO, FIFO, 우선순위 |

종류가 많아 보여도 실제 선택 질문은 세 개다.

```text
순서대로 담을 건가?
key나 값으로 찾을 건가?
꺼내는 규칙이 정해져 있나?
```

---

## 우선순위

| 우선순위 | 우선 볼 것 | 이유 |
| --- | --- | --- |
| 1순위 | `vector` | 가장 흔한 “저장 + 순회 + 인덱스 접근” 기본값 |
| 2순위 | `unordered_map`, `unordered_set` | key 검색과 존재 확인에서 자주 사용 |
| 3순위 | `map`, `set` | 정렬된 순서나 범위 검색이 필요할 때 |
| 4순위 | `deque` | 앞뒤 삽입·삭제가 중요할 때 |
| 특수 | `array`, `list`, `stack`, `queue`, `priority_queue` | 조건이 명확할 때 선택 |

> [!important]
> `std::list`는 “중간 삽입·삭제가 O(1)”이라는 이유만으로 고르지 않는다. 위치를 찾는 순회 비용과 캐시 비용까지 같이 봐야 한다.

---

## 빠른 선택표

| 가장 중요한 요구 | 먼저 볼 컨테이너 |
| --- | --- |
| 많이 담고 자주 순회 | `std::vector` |
| key로 빠르게 찾음, 순서 필요 없음 | `std::unordered_map` |
| 값의 존재 여부만 빠르게 확인 | `std::unordered_set` |
| key 정렬 또는 범위 검색 필요 | `std::map` |
| 중복 없는 값을 정렬된 순서로 유지 | `std::set` |
| 앞과 뒤에서 넣고 뺌 | `std::deque` |
| 크기가 고정 | `std::array` |
| 정해진 방식으로만 꺼냄 | `std::stack`, `std::queue`, `std::priority_queue` |
| 중간 삽입·삭제와 주소 안정성이 정말 중요 | `std::list` 검토 |

---

## 선택할 때 같이 보는 것

| 기준 | 봐야 하는 이유 |
| --- | --- |
| 가장 자주 하는 작업 | 순회, 검색, 삽입, 삭제 중 무엇이 중심인지가 선택을 결정한다. |
| 메모리 배치 | 연속 메모리는 순회와 캐시 효율에 유리하다. |
| 인덱스 접근 | `vector`, `array`, `deque`는 가능하지만 `list`, `map`, `set`은 다르다. |
| 정렬 필요 여부 | 정렬된 순서가 필요하면 `map`, `set` 또는 정렬된 `vector`를 검토한다. |
| 중복 허용 여부 | 중복 없는 값 모음이면 `set` 계열이 맞다. |
| 주소/반복자 안정성 | 컨테이너에 따라 삽입·삭제 후 기존 포인터와 반복자가 무효화될 수 있다. |

`Big-O`는 중요하지만 전부는 아니다. `vector` 순회와 `list` 순회는 둘 다 `O(N)`이지만, `vector`는 연속 메모리라 캐시에 유리하고 `list`는 노드 포인터를 따라가야 해서 실제 순회가 느릴 수 있다.

---

## 1순위: `std::vector`

| 항목 | 내용 |
| --- | --- |
| 역할 | 크기가 변하는 동적 배열 |
| 구조 | 원소가 연속된 메모리에 저장됨 |
| 강점 | 전체 순회, 인덱스 접근, 끝에 추가 |
| 약점 | 중간 삽입·삭제 시 뒤쪽 원소 이동, 재할당 시 주소 무효화 가능 |
| 선택 기준 | **많이 담고 자주 순회하면 `vector`부터 시작한다.** |

`vector`가 기본값인 이유는 실제 코드에서 “모아두고 순서대로 읽는” 데이터가 많기 때문이다. 원소가 연속되어 있어 다음 원소 접근을 CPU가 예측하기 쉽고, 캐시 라인에도 주변 원소가 함께 들어올 가능성이 높다.

개수를 대략 알고 있다면 `reserve()`로 재할당을 줄일 수 있다. 반대로 중간 삭제가 잦다면 매번 뒤쪽 원소가 앞으로 이동한다는 점을 고려해야 한다.

## 2순위: 검색과 존재 확인

### `std::unordered_map`

| 항목 | 내용 |
| --- | --- |
| 역할 | key로 value를 빠르게 찾는 해시 테이블 |
| 구조 | key → hash → bucket → value |
| 강점 | 순서가 필요 없는 빠른 key 검색 |
| 약점 | 정렬 순서 없음, 해시 충돌과 rehash 비용 |
| 선택 기준 | **순서 필요 없는 key 검색은 `unordered_map`.** |

ID로 플레이어를 찾거나, 이름으로 데이터를 찾는 식의 “key로 바로 접근”하는 문제에 잘 맞는다. 평균적으로 검색이 빠르지만, 원소가 늘어나 rehash가 발생하면 반복자가 무효화될 수 있다.

### `std::unordered_set`

| 항목 | 내용 |
| --- | --- |
| 역할 | 중복 없는 값의 존재 여부를 빠르게 확인하는 해시 집합 |
| 구조 | value → hash → bucket |
| 강점 | 방문 여부, 중복 방지, 빠른 존재 확인 |
| 약점 | 정렬 순서 없음, rehash 비용 |
| 선택 기준 | **순서 필요 없는 존재 확인은 `unordered_set`.** |

`map`은 key로 value를 찾지만, `set`은 값 자체가 key 역할을 한다. BFS 방문 체크, 이미 처리한 ID 확인처럼 “있나 없나”가 핵심이면 `unordered_set`을 먼저 본다.

---

## 3순위: 정렬이 필요할 때

### `std::map`

| 항목 | 내용 |
| --- | --- |
| 역할 | key를 정렬된 순서로 유지하는 key-value 컨테이너 |
| 구조 | 정렬된 트리 구조 |
| 강점 | 정렬 순회, 범위 검색, `lower_bound` |
| 약점 | 단순 검색만 보면 `unordered_map`보다 불리할 수 있음 |
| 선택 기준 | **정렬된 key나 범위 검색이 필요하면 `map`.** |

`map`은 key가 정렬된 상태로 유지된다. 특정 점수 이상, 특정 ID 범위, 정렬된 순회처럼 key 순서가 의미를 가지면 `map`이 자연스럽다.

### `std::set`

| 항목 | 내용 |
| --- | --- |
| 역할 | 중복 없는 값을 정렬된 순서로 유지하는 집합 |
| 구조 | 정렬된 트리 구조 |
| 강점 | 정렬 순회, 범위 검색, 중복 방지 |
| 약점 | 정렬이 필요 없으면 `unordered_set`보다 불필요할 수 있음 |
| 선택 기준 | **정렬된 집합은 `set`.** |

중복을 막으면서 정렬된 순서가 필요할 때 사용한다. 값의 존재 여부만 빠르게 확인하면 되는 상황이라면 `unordered_set`이 더 자연스럽다.

---

## 4순위: 앞뒤 삽입·삭제

### `std::deque`

| 항목 | 내용 |
| --- | --- |
| 역할 | 앞과 뒤에서 넣고 빼기 좋은 컨테이너 |
| 구조 | 여러 블록을 이어 붙인 형태에 가까움 |
| 강점 | `push_front`, `pop_front`, `push_back`, `pop_back` |
| 약점 | `vector`처럼 완전한 한 덩어리 연속 메모리는 아님 |
| 선택 기준 | **앞뒤로 드나들면 `deque`.** |

`vector`는 앞쪽에 원소를 넣으면 기존 원소들을 뒤로 밀어야 한다. 반면 `deque`는 앞과 뒤의 삽입·삭제를 처리하기 좋게 설계되어 있다. 슬라이딩 윈도우, 양방향 큐처럼 양 끝 작업이 중심이면 고려한다.

## 특수한 경우

### `std::array`

| 항목 | 내용 |
| --- | --- |
| 역할 | 크기가 컴파일 타임에 정해진 고정 배열 |
| 구조 | 연속 메모리, 크기 `N`이 타입에 포함됨 |
| 강점 | 고정 크기 데이터, `size()`, `begin()`, `end()` 사용 가능 |
| 약점 | 실행 중 크기 변경 불가 |
| 선택 기준 | **고정 크기면 `array`, 변하는 크기면 `vector`.** |

`std::array<int, 3>`과 `std::array<int, 4>`는 서로 다른 타입이다. 작은 고정 테이블, 방향 벡터, 고정 개수 슬롯처럼 크기가 변하지 않는 데이터에 잘 맞는다.

### `std::list`

| 항목 | 내용 |
| --- | --- |
| 역할 | 노드들이 포인터로 연결된 양방향 연결 리스트 |
| 구조 | 각 원소가 별도 노드, 노드끼리 연결 |
| 강점 | 위치를 이미 알 때 중간 삽입·삭제, 노드 주소 안정성 |
| 약점 | 인덱스 접근 불가, 순회 비용과 캐시 비용이 큼 |
| 선택 기준 | **위치를 이미 아는 중간 삽입·삭제나 주소 안정성이 필요할 때만 검토한다.** |

`list`의 중간 삽입·삭제가 빠르다는 말은 “그 위치의 반복자를 이미 알고 있다”는 전제가 붙는다. 삭제할 위치를 찾기 위해 매번 처음부터 순회한다면 그 비용이 커진다.

전체 순회가 많으면 `vector`가 더 나은 경우가 많다. 죽은 객체 제거 같은 문제도 처음부터 `list`로 바꾸기보다 `vector + erase-remove idiom`, swap-remove, 활성 플래그, object pool을 먼저 검토한다.

### 컨테이너 어댑터

| 어댑터 | 규칙 | 꺼내는 방식 |
| --- | --- | --- |
| `std::stack` | LIFO | 나중에 넣은 것을 먼저 꺼냄 |
| `std::queue` | FIFO | 먼저 넣은 것을 먼저 꺼냄 |
| `std::priority_queue` | 우선순위 기준 | 우선순위가 높은 것을 먼저 꺼냄 |

어댑터는 내부 컨테이너를 감싸서 특정 사용 방식만 제공한다. 직접 순회하거나 중간 원소를 지워야 한다면 어댑터보다 기본 컨테이너를 사용한다.

---

## 자주 헷갈리는 비교

| 비교 | 기준 |
| --- | --- |
| `vector` vs `list` | 순회가 많으면 `vector`, 위치를 이미 아는 중간 삽입·삭제가 핵심이면 `list` 검토 |
| `map` vs `unordered_map` | 순서 필요 없으면 `unordered_map`, 정렬/범위 검색 필요하면 `map` |
| `set` vs `unordered_set` | 순서 필요 없으면 `unordered_set`, 정렬/범위 검색 필요하면 `set` |
| `vector` vs `deque` | 전체 순회 중심이면 `vector`, 앞뒤 삽입·삭제 중심이면 `deque` |

---

## 반복자와 주소 안정성

| 컨테이너 | 주의할 점 |
| --- | --- |
| `vector` | 재할당되면 기존 주소가 바뀔 수 있음 |
| `deque` | 삽입·삭제 위치에 따라 규칙이 복잡함 |
| `list` | 지운 원소 외의 노드는 비교적 안정적 |
| `map`, `set` | 지운 원소 외의 노드는 비교적 안정적 |
| `unordered_map`, `unordered_set` | rehash가 일어나면 반복자 무효화 가능 |

주소나 반복자를 오래 들고 있어야 한다면 컨테이너별 무효화 규칙을 따로 확인해야 한다. 이 부분은 성능만큼이나 버그와 직결된다.

---

## 사용 예시

| 상황 | 선택 |
| --- | --- |
| 매 프레임 적 목록 전체 순회 | `vector`, Unreal `TArray` |
| ID로 플레이어 찾기 | `unordered_map`, Unreal `TMap` |
| 방문한 노드 체크 | `unordered_set` |
| 정렬된 랭킹 순회 | 정렬된 `vector`, `map`, `multimap` |
| 죽은 객체 제거 | `vector` + erase-remove idiom, object pool 검토 |

랭킹처럼 점수가 중복될 수 있는 데이터는 `map` 하나로 표현하기 애매할 수 있다. 점수와 ID를 같이 정렬하거나, 중복 key가 필요하면 `multimap`, 단순 표시용이면 `vector`를 정렬하는 방식도 검토한다.

## 선택 요약

| 컨테이너 | 선택 기준 |
| --- | --- |
| `vector` | 많이 담고 순회하거나 인덱스로 접근 |
| `unordered_map` | 순서가 필요 없는 key-value 검색 |
| `unordered_set` | 순서가 필요 없는 존재 여부 확인 |
| `map` | key 정렬, 범위 검색 |
| `set` | 정렬된 존재 여부 확인 |
| `deque` | 앞과 뒤에서 삽입·삭제 |
| `array` | 크기가 컴파일 타임에 고정 |
| `list` | 위치를 이미 아는 중간 삽입·삭제, 주소 안정성 |

컨테이너 선택은 결국 이 질문으로 돌아온다.

```text
가장 자주 하는 작업이 무엇인가?
그 작업이 이 컨테이너의 구조와 잘 맞는가?
```
