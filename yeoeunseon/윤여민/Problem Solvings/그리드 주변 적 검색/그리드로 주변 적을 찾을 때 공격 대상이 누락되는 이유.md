## 문제 상황

전장의 적 **20,000명**을 관리한다. 매번 모든 적과 거리를 비교하는 대신, 전장을 **4m × 4m 그리드 칸**으로 나누었다.

각 적은 현재 위치의 올바른 칸에 한 번씩 등록되어 있다. 적이 다른 칸으로 이동하면 등록도 정상적으로 옮긴다.

```cpp
std::vector<int> FindNearbyEnemies(
    double PlayerX, double PlayerY, double Radius)
{
    std::vector<int> Hits;

    const int CellX = static_cast<int>(PlayerX / 4.0);
    const int CellY = static_cast<int>(PlayerY / 4.0);

    for (const Enemy& E : Grid.At(CellX, CellY))
    {
        const double dx = E.X - PlayerX;
        const double dy = E.Y - PlayerY;

        if (dx * dx + dy * dy <= Radius * Radius)
        {
            Hits.push_back(E.Id);
        }
    }

    return Hits;
}
```

`Grid.At(x, y)`는 **해당 칸 하나의 적 목록**을 반환한다. 빈 칸이면 빈 목록을 반환하며, 검색 중에는 위치와 목록이 바뀌지 않는다.

QA에서 다음과 같이 보고했다.

> 적이 분명 공격 범위 안에 있는데, 플레이어 위치에 따라 검색 결과에서 빠집니다.

- 전장에는 음수 좌표도 있다.
- 공격 반경은 스킬마다 다르다.
- 적은 퍼져 있을 수도, 좁은 장소에 몰릴 수도 있다.
- 적은 몸체 크기 없는 점으로 취급한다.

**누락 원인을 찾고 수정 방향을 설명해라. 전체 순회보다 유리하거나 불리한 조건도 설명해라.**

좌표와 반경은 유한하고 계산 가능한 범위이며, 반경은 음수가 아니다. 성능은 아직 측정하지 않았다.

## 풀이 — 생각을 마친 뒤 열기

> [!question]- 어떤 목록을 검사하고 있었을까?
> ### 1. 먼저 정수 변환을 의심했다
>
> “문제 없어 보이는데 static_cast<int> 때문인가? floor해야 되는 거라서?”
>
> 맞았다. 정수 변환은 소수 부분을 버리므로 음수에서 내림과 다르다.
>
> ```text
> x = −0.1, 칸 폭 = 4
>
> 정수 변환: −0.025 →  0
> 내림:      −0.025 → −1
>
> −1번 칸: −4 ≤ x < 0
>  0번 칸:  0 ≤ x < 4
> ```
>
> **floor로 계산해야 음수에서도 올바른 칸을 찾는다.** 하지만 이것만 고쳐도 양수 좌표에서의 누락은 남는다.
>
> ---
>
> ### 2. 주변 칸을 가져오는 코드로 읽었다
>
> 플레이어 `(3.9, 1)`, 적 `(4.1, 1)`, 반경 `2m`라면:
>
> ```text
> 플레이어 → 칸 (0, 0)
> 적       → 칸 (1, 0)
> 실제 거리 → 0.2m
> ```
>
> 처음에는 이 적도 방문한다고 답했다. `Grid.At()`이 주변 범위의 목록을 가져오는 의미라고 생각했기 때문이다.
>
> 실제 실행되는 것은 `Grid.At(0, 0)`뿐이다. **적이 들어 있는 다른 칸은 방문하지 않아, 거리 검사 자체를 하지 못한다.**
>
> 여기서 수정 방향을 정리했다.
>
> “floor로 바꾸고, 범위 내의 각 그리드 목록 순회로 바꾼다.”
>
> 코드를 읽을 때는 **가져오는 목록의 범위 → 반복 대상 → 최종 조건**을 구분해야 했다. 거리 조건이 맞아도 반복 대상에서 빠진 적은 찾을 수 없다.
>
> ---
>
> ### 3. 방문할 칸 범위를 구한다
>
> **공격 원을 감싸는 사각형**의 양 끝을 칸 번호로 바꾼다. 이 사각형은 그리드 칸 하나가 아니라, 검색을 위해 계산한 범위다.
>
> ```text
> x범위: PlayerX − Radius ~ PlayerX + Radius
> y범위: PlayerY − Radius ~ PlayerY + Radius
>
> 각 경계에 floor(좌표 / 칸 폭) 적용
> → 최소·최대 칸 번호 사이를 순회
> → 각 칸의 적마다 거리 제곱 검사
> ```
>
> 반경이 달라지면 방문할 칸 수도 달라진다. 항상 주변 9칸으로 고정하지 않는다.
>
> ```cpp
> // <cmath>, <vector> 필요. Enemy와 Grid는 별도로 정의한다.
> std::vector<int> FindNearbyEnemies(
>     double PlayerX, double PlayerY, double Radius)
> {
>     constexpr double CellSize = 4.0;
>     const double RadiusSquared = Radius * Radius;
>     std::vector<int> Hits;
>
>     // 원을 감싼 사각형의 양 끝을 칸 번호로 변환한다. floor 후 int에 담는다.
>     const int MinX = static_cast<int>(std::floor((PlayerX - Radius) / CellSize));
>     const int MaxX = static_cast<int>(std::floor((PlayerX + Radius) / CellSize));
>     const int MinY = static_cast<int>(std::floor((PlayerY - Radius) / CellSize));
>     const int MaxY = static_cast<int>(std::floor((PlayerY + Radius) / CellSize));
>
>     // cy는 행, cx는 열. 최소~최대 범위의 모든 칸을 방문한다.
>     for (int cy = MinY; cy <= MaxY; ++cy)
>     {
>         for (int cx = MinX; cx <= MaxX; ++cx)
>         {
>             // 지금 방문한 한 칸에 등록된 적들을 확인한다.
>             for (const Enemy& E : Grid.At(cx, cy))
>             {
>                 const double dx = E.X - PlayerX;
>                 const double dy = E.Y - PlayerY;
>
>                 // 사각형의 후보 중 실제 공격 원 안에 있는 적만 남긴다.
>                 if (dx * dx + dy * dy <= RadiusSquared)
>                 {
>                     Hits.push_back(E.Id);
>                 }
>             }
>         }
>     }
>
>     return Hits;
> }
> ```
>
> 사각형 모서리 쪽의 적도 후보에 들어올 수 있다. **후보는 넓게 모으고, 원 안인지 거리로 최종 판정한다.** 제곱한 값을 비교하므로 제곱근은 필요 없다.
>
> 위 코드는 Grid/Enemy 정의가 필요한 설명용 발췌다. 같은 검색 방식을 별도 일반 C++ 테스트로 구현해 전체 순회와 결과를 비교했다. 정수 칸 번호와 반복문의 증가가 넘치지 않는 범위를 전제로 한다.

## 왜 사각형으로 칸을 고를까?

> [!info]- 원으로 더 걸러내면 무조건 낫지 않을까?
> **사각형은 시작·끝 칸을 한 번 구하면, 그 사이를 순회하면 된다.**
>
> 원으로 더 정밀하게 고르려면 후보 칸마다 원과 겹치는지 추가로 검사해야 한다. 각 칸 안에서 플레이어와 가장 가까운 점을 구하고, 그 점까지의 거리 제곱을 반경 제곱과 비교하는 방식이다.
>
> ```text
> 사각형 방식
> 칸 범위 계산 → 해당 칸의 적에게 거리 검사
>
> 원으로 추가 거르기
> 칸 범위 계산 → 칸마다 원과 겹치는지 검사
>              → 남은 칸의 적에게 거리 검사
> ```
>
> “어차피 걸친 칸의 모든 적을 검사하는데 왜 차이가 있지?”라고 물었다. **같은 칸이 남으면 적 검사도 같고, 원과 안 겹치는 칸을 통째로 생략할 때만 적 검사를 아낀다.**
>
> 계산 예시에서 칸 폭 4m, 중심 `(10, 10)`, 반경 8m일 때 사각형은 25칸, 원으로 거르면 21칸이었다. 칸마다 적 10명을 가정하면 적 검사는 250 → 210회지만, 원–칸 검사 25회가 추가된다.
>
> 반면 처음의 중심 `(3.9, 1)`, 반경 2m 예시는 두 방식 모두 4칸이다. 이때는 원–칸 검사만 추가되고 생략할 칸은 없다.
>
> **원 검사가 복잡해서 못 쓰는 것이 아니다. 추가 검사로 아끼는 비용이 클 때 선택한다.** 위 숫자는 기하 계산 예시이며 실행 시간 측정이 아니다.

## 결론

**floor로 칸을 구하고, 공격 범위에 걸친 칸들을 순회한 뒤, 적마다 거리로 최종 판정한다.**

마지막으로 직접 정리한 답은 다음과 같았다.

> 검사할 적을 전체 순회보다 훨씬 줄이면 이득이고, 비슷하면 이득이 작거나 불리하다.

처음에는 “검사 수가 비슷하면 그냥 같은 것 아닌가?”라고 생각했다. 하지만 그리드는 칸 조회 외에도 적 등록·칸 이동·삭제 관리가 필요하다.

```text
그리드의 이득 = 생략한 적들의 거리 검사 비용
그리드의 추가 비용 = 칸 조회 + 등록·이동·삭제 관리

많이 생략한다 → 추가 비용을 내고도 유리할 수 있음
거의 다 본다 → 관리 비용만 더해져 불리할 수 있음
```

적이 많이 퍼져 있고 좁은 주변 검색을 반복하면 후보를 크게 줄일 수 있다. 반대로 적이 한곳에 몰리거나 반경이 커서 대부분을 검사하면 이득이 작다. 검색이 드물면 등록을 유지하는 비용도 상대적으로 중요해진다.

칸을 작게 하면 방문할 칸 수가 늘고, 크게 하면 칸당 후보가 늘 수 있다. **칸 크기 하나를 정답으로 외우지 않고 검색과 갱신 비용을 함께 비교한다.** 이번에는 실행 시간을 측정하지 않았으므로 성능 향상을 확정하지 않는다.

### 이름만 보고 떠올릴 것

```text
공간 분할 → 위치별로 검색 후보 축소
그리드    → 같은 크기의 칸과 적 목록
floor     → 음수에서도 내림으로 칸 계산
Grid.At   → 한 칸의 목록, 주변 전체가 아님
칸 범위   → 원을 감싼 사각형의 최소~최대 칸
거리 제곱 → 원 안인지 최종 판정
이동      → 칸이 바뀌면 등록도 옮김
비용      → 줄인 검사 vs 추가 관리
```

이번 검색은 적의 중심 위치만 다룬다. 몸체가 공격 범위에 닿는지까지 판단하는 완전한 충돌 검사는 아니다. 검색 중 위치·목록이 바뀌지 않고, 각 적이 현재 칸에 한 번씩 등록되어 있다는 전제가 필요하다.
