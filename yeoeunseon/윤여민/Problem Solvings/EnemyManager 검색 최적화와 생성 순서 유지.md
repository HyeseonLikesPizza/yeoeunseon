# EnemyManager 검색 최적화와 생성 순서 유지

## 문제 상황

언리얼 게임에서 적 상태를 다음처럼 관리하고 있다.

```cpp
struct FEnemyState
{
    int32 EnemyId;
    float HP;
    FVector Position;
};

TArray<FEnemyState> Enemies;
```

특정 적은 `EnemyId`로 찾는다.

```cpp
FEnemyState* FindEnemy(int32 EnemyId)
{
    for (FEnemyState& Enemy : Enemies)
    {
        if (Enemy.EnemyId == EnemyId)
        {
            return &Enemy;
        }
    }

    return nullptr;
}
```

적이 많아지자 프로파일링에서 **`FindEnemy()`가 자주 호출되면서 비용이 커지고 있는 것**을 발견했다.

여러 시스템이 이 함수를 사용한다.

```text
AI
투사체
UI
```

UI에는 이런 코드도 있다.

```cpp
if (EnemyManager.FindEnemy(EnemyId))
{
    float HP =
        EnemyManager.FindEnemy(EnemyId)->HP;
}
```

적은 전투 중 추가되고 삭제된다.

```cpp
Enemies.Add(NewEnemy);
Enemies.RemoveAt(Index);
```

그리고 중요한 요구사항이 하나 있다.

> **Enemies는 적이 생성된 순서를 유지해야 한다.**

한 개발자가 반복 검색을 없애기 위해 다음처럼 수정했다.

```cpp
FEnemyState* CachedTarget;
```

그런데 **적이 많이 추가된 직후 `CachedTarget`을 사용할 때 가끔 크래시가 발생한다.**

### 해결 조건

이 시스템을 개선해라.

단순히 `FindEnemy()`만 빠르게 만드는 것이 아니라 다음을 모두 고려해야 한다.

```text
EnemyId 검색
전체 순회
적 추가
적 삭제
생성 순서 유지
참조의 안전성
```

그리고 해결책을 하나 제시할 때마다:

> **“이 해결책 때문에 새로 생기는 문제는 무엇인가?”**

를 확인해라.

## 풀이 — 생각을 마친 뒤 열기

> [!question]- 1부 — 병목과 가장 작은 개선
> ### STEP 1 — 첫 번째로 확인할 것
>
> **상황**
>
> `FindEnemy()`는 `TArray`를 처음부터 훑는다. 적이 많아지고 AI·투사체·UI가 반복 호출하면 한 번의 작은 비용이 계속 누적된다.
>
> ---
>
> **아이디어**
>
> Binary Search나 `TMap`으로 조회 자체를 빠르게 만들 수 있는지 비교한다.
>
> **확인할 조건**
>
> 검색 속도만 비교해서는 부족하다. 적의 추가·삭제, 생성 순서, 외부 참조의 안전성도 함께 지켜야 한다.
>
> **다음**
>
> 검색 방식을 바꾸기 전에 호출 코드 안의 불필요한 검색부터 줄일 수 있을까?
>
> ### STEP 2 — 가장 작은 개선은?
>
> **상황**
>
> UI 코드는 같은 `EnemyId`를 확인한 뒤 다시 한 번 찾는다.
>
> ---
>
> **아이디어**
>
> 한 번 찾은 결과를 같은 코드 블록 안에서 바로 재사용한다.
>
> **좋아지는 점**
>
> - 자료구조를 바꾸지 않아도 검색 횟수를 줄인다.
> - 참조를 짧은 범위에서만 사용하므로 수명 정책도 바뀌지 않는다.
>
> **핵심**
>
> 더 빠른 자료구조를 찾기 전에 불필요한 작업부터 제거한다.
>
> **다음**
>
> 한 번 찾은 `FEnemyState*`를 더 오래 보관하면 검색 자체를 없앨 수 있을까?
>
> ### STEP 3 — 첫 번째 구조 변경 후보
>
> **상황**
>
> Linear Search의 비교 횟수를 줄이려면 Binary Search가 자연스러운 후보가 된다.
>
> ---
>
> **아이디어**
>
> 실제 `Enemies` 배열을 `EnemyId` 기준으로 정렬한다.
>
> **새 문제**
>
> ```text
> 생성 순서 [30, 10, 40, 20]
>               ↓ 정렬
> 검색 순서 [10, 20, 30, 40]
> ```
>
> Binary Search는 빨라지지만, 배열이 보존해야 하는 생성 순서가 사라진다.
>
> **핵심**
>
> 빠른 알고리즘에도 전제조건이 있으며, 그 조건이 기존 요구사항과 충돌할 수 있다.
>
> **다음**
>
> 배열 순서를 바꾸지 않고 검색을 피하기 위해 찾은 주소를 캐시하면 어떨까?

> [!question]- 2부 — 구조 변경 후보 검증
> ### STEP 4 — 그 해결책의 수명은 안전한가?
>
> **상황**
>
> 같은 적을 반복해서 찾는 비용을 없애기 위해 `FEnemyState* CachedTarget`을 저장한다.
>
> ---
>
> **아이디어**
>
> 한 번 얻은 주소를 다음 호출에서도 계속 사용한다.
>
> **새 문제**
>
> `TArray::Add()` 중 Capacity가 부족하면 내부 저장 공간이 재할당될 수 있다. 기존 원소의 주소가 바뀌면 이전 주소를 보관한 `CachedTarget`은 안전하지 않다.
>
> > 검색 비용을 없앤 대신 참조 수명과 무효화 문제를 만들었다.
>
> **다음**
>
> 주소 대신 `EnemyId -> Array Index`를 저장하면 재할당 문제를 피할 수 있을까?
>
> ### STEP 5 — 주소를 쓰지 않는다면?
>
> ---
>
> **아이디어**
>
> `EnemyId -> Array Index`를 저장한다.
>
> **좋아지는 점**
>
> - `TArray` 재할당으로 원소 주소가 바뀌어도 Index 자체는 주소가 아니다.
> - `EnemyId`로 배열 위치를 빠르게 찾을 수 있다.
>
> **새 문제**
>
> ```text
> [100, 200, 300, 400]
>        ↓ 200 삭제
> [100, 300, 400]
>
> 기존 Map : 300 -> 2
> 실제 위치: 300 -> 1
> ```
>
> `RemoveAt()`이 뒤쪽 원소를 앞으로 당기므로 저장된 Index가 실제 위치와 달라진다.
>
> **다음**
>
> 원소를 당기지 않는 `RemoveAtSwap()`을 쓰면 Index 갱신 범위를 줄일 수 있을까?
>
> ### STEP 6 — 삭제 비용을 줄일 수 있을까?
>
> ---
>
> **아이디어**
>
> 마지막 원소 하나만 삭제된 자리로 옮긴다.
>
> **좋아지는 점**
>
> 수정해야 할 Index가 많은 뒤쪽 원소 전체에서, 이동한 마지막 원소 하나로 줄어든다.
>
> **새 문제**
>
> ```text
> [100, 200, 300, 400]
>        ↓ 200 RemoveAtSwap
> [100, 400, 300]
>
> 원하는 생성 순서: [100, 300, 400]
> ```
>
> 삭제 비용은 줄지만 생성 순서 요구사항을 깨뜨린다.
>
> **핵심**
>
> 연산 비용을 줄이는 방법이 반드시 요구사항을 만족하는 방법은 아니다.
>
> **다음**
>
> 검색과 생성 순서를 하나의 컨테이너가 모두 책임지지 않게 만들면 어떨까?

> [!question]- 3부 — 요구사항을 다시 설계하기
> ### STEP 7 — 요구사항을 다시 나눠보자
>
> ---
>
> **핵심 발견**
>
> 검색과 생성 순서 유지는 서로 다른 요구사항이다.
>
> **설계**
>
> - `TMap<int32, FEnemyState>`: `EnemyId` 검색과 살아 있는 적의 상태
> - `TArray<int32> CreationOrder`: 생성 순서
> - 외부 시스템: raw pointer 대신 `EnemyId`를 보관하고 필요할 때 다시 조회
>
> **좋아지는 점**
>
> 검색 구조를 바꿔도 Order 배열의 생성 순서는 그대로 유지된다.
>
> **다음**
>
> Order 배열에서 삭제된 ID를 즉시 `RemoveAt()`하지 않고 남겨두면 삭제 비용도 피할 수 있을까?
>
> ### STEP 8 — 새로 생긴 비용은?
>
> ---
>
> **아이디어**
>
> Map에서는 적을 즉시 제거하고 `CreationOrder`에는 삭제된 ID를 Tombstone으로 남긴다. 순회할 때 Map에 존재하는 ID만 처리한다.
>
> **좋아지는 점**
>
> - 삭제할 때 Order 배열의 원소를 당기지 않는다.
> - 살아 있는 적의 생성 순서는 유지된다.
>
> **새 문제**
>
> Tombstone이 쌓일수록 살아 있는 적보다 더 많은 ID를 검사하게 된다.
>
> **다음**
>
> 전투 중에는 삭제 비용을 미루고, 안전한 시점에 한꺼번에 정리할 수 있을까?
>
> ### STEP 9 — 그 비용은 언제 지불할까?
>
> ---
>
> **아이디어**
>
> 전투·웨이브 종료 시점이나 Tombstone 비율이 임계치를 넘었을 때 Order 배열을 `Compact`한다.
>
> **결론**
>
> 비용을 없앤 것이 아니라 지불 시점을 옮겼다. 전투 중에는 삭제 비용을 분산하고, 여유 있는 시점에는 누적된 순회 비용을 정리한다.
>
> > 현재 요구사항에서 도달한 답은 단순히 “`TArray` 대신 `TMap`을 쓴다”가 아니다. 검색·순서·삭제·참조 수명을 역할별로 분리하고, 그 과정에서 생긴 비용을 운영 시점에 맞춰 통제하는 것이 핵심이다.

## 핵심 결론

> [!success]- 최종 결론 확인하기
> **한 줄 결론**
>
> 불필요한 `Find`를 먼저 줄이고, 검색과 생성 순서를 서로 다른 구조에 맡긴다.
>
> ```text
> TMap<int32, FEnemyState>  → EnemyId 검색과 살아 있는 상태
> TArray<int32> CreationOrder → 생성 순서
> 외부 시스템                → raw pointer 대신 EnemyId 저장 후 재조회
> 삭제                       → Map 즉시 제거 / Order에는 Tombstone 유지
> 정리                       → 안전한 시점이나 임계치에서 Compact
> ```
>
> **대가**
>
> Tombstone 순회와 간헐적인 `Compact` 비용이 생긴다. Map과 Order의 일관성도 함께 관리해야 한다.

## 해설 2 — 테스트 검증

> [!example]- 테스트 전체 보기
> ### 테스트 실행 정보
>
> 제공된 성공 로그는 이름 변경 전 경로인 `TestProject.CppTest`에서 실행한 결과다. 현재 테스트 파일은 `EnemyManagerSearchProblemTest.cpp`, Automation 경로는 `TestProject.ProblemSolving.EnemyManagerSearchProblem`이다. 검증할 현상은 유지하되, 코드 자체도 문제 → 질문 → 관찰 → 다음 질문 순서로 읽히도록 재구성했다.
>
> ### 1. 검색 비용 비교
>
> **확인**
>
> `RunSearchStrategyComparison()`은 같은 조회를 Linear Search, Binary Search, `TMap`으로 수행한다.
>
> ```text
> Linear 15.234 ms / avg 4991.50 comparisons
> Binary 0.336 ms / avg 12.37 comparisons
> TMap 0.025 ms
> ```
>
> **결과**
>
> Linear Search는 조회 한 번에 평균 약 5천 번 비교했다. Binary Search는 약 12번으로 줄었고 `TMap`의 측정 시간은 가장 짧았다.
>
> **검증 범위**
>
> 세 방식의 checksum도 비교하므로, 단지 빨리 끝난 것이 아니라 같은 적을 찾았는지도 확인한다.
>
> **다음**
>
> 검색 방식을 바꾸기 전에 중복 호출을 제거했을 때의 효과를 측정한다.
>
> ### 2. 중복 조회 제거
>
> **확인**
>
> `RunDuplicateLookupExperiment()`은 UI의 중복 호출을 그대로 재현한다.
>
> ```text
> 1,999,800 comparisons -> 999,900 comparisons
> ```
>
> **결과**
>
> 한 번 찾은 결과를 같은 범위에서 재사용하자 비교 횟수가 정확히 절반이 됐다.
>
> **해석**
>
> 저장 구조나 수명 정책을 바꾸지 않으므로 가장 먼저 적용할 수 있는 안전한 최적화다.
>
> ### 3. Binary Search의 정렬 조건
>
> **확인**
>
> `RunBinarySearchOrderingExperiment()`은 실제 배열을 `EnemyId` 기준으로 정렬한다.
>
> ```text
> 생성 순서 [30, 10, 40, 20]
> → 정렬 후 [10, 20, 30, 40]
> ```
>
> **새 문제**
>
> Binary Search는 빨라지지만 생성 순서가 사라진다. 시간 측정만 봤다면 놓쳤을 제약이다.
>
> ### 4. raw pointer 캐시의 무효화
>
> **확인**
>
> `RunRawPointerInvalidationExperiment()`은 초기 Capacity가 작도록 `Reserve(1)`한 뒤 원소를 추가해 재할당을 유도한다.
>
> ```text
> TArray Capacity 1 -> 18 / 첫 원소 주소 변경 = YES
> ```
>
> **결과**
>
> 원소의 값은 남아 있어도 저장 위치가 이동했다. 재할당 전에 얻은 `FEnemyState*`를 이후에도 사용할 수 있다는 보장은 없다.
>
> **해석**
>
> `CachedTarget` 크래시는 검색 로직이 아니라 **컨테이너 변경 이후에도 오래된 주소를 사용한 수명 문제**다.
>
> ### 5. Index Map의 삭제 후 불일치
>
> **확인**
>
> `RunIndexInvalidationExperiment()`에서는 `EnemyId -> Index` Map을 만든 뒤 배열의 두 번째 적을 `RemoveAt()`으로 삭제한다.
>
> ```text
> [100, 200, 300, 400] -> [100, 300, 400]
> Map의 Enemy 300 위치=2, 실제 위치=1
> ```
>
> **결과**
>
> 주소 대신 Index를 저장해 재할당 문제는 피했지만, 삭제로 배열이 당겨지면서 저장된 Index가 낡았다. 테스트의 `StoredIndex != ActualIndex` 검증은 이 불일치를 의도적으로 확인한다.
>
> **새 비용**
>
> 현재처럼 순서를 유지하는 `RemoveAt()`을 사용한다면 이동한 원소들의 Index를 갱신하거나 Index를 다시 구축해야 한다.
>
> ### 6. RemoveAtSwap과 생성 순서
>
> **확인**
>
> `RunSwapRemovalOrderingExperiment()`은 두 번째 적을 `RemoveAtSwap()`으로 지운다.
>
> ```text
> [100, 200, 300, 400] -> [100, 400, 300]
> 원하는 생성 순서=[100, 300, 400]
> ```
>
> **결과**
>
> 많은 원소를 당기지는 않지만 마지막 원소가 빈자리로 이동한다.
>
> **새 문제**
>
> Index 갱신 범위는 작아져도 생성 순서 요구사항이 깨진다. 이 문제에서는 빠른 삭제만으로 올바른 해결책이 될 수 없다.
>
> ### 7~9. 역할 분리, Tombstone, Compact
>
> **확인**
>
> `RunLazyCompactionExperiment()`은 상태를 `TMap`에 두고 생성 순서는 ID 배열에 둔다. 20,000개 중 75%를 Map에서 삭제한 뒤, Order 배열에는 Tombstone을 남겨 둔다.
>
> ```text
> Alive=5,000 / Tombstone=15,000
> Compact 전 1,000,000 checks, 0.723 ms
> Compact 후   250,000 checks, 0.313 ms
> Compact 비용 0.021 ms
> ```
>
> **결과**
>
> Compact 전에는 살아 있는 적이 5천 개뿐이어도 매 순회마다 2만 개의 ID를 확인한다. Compact 후에는 실제 생존자만 남아 검사 횟수가 4분의 1이 됐다.
>
> **검증 범위**
>
> 시간값은 실행 환경에 따라 달라지지만 검사 횟수의 변화는 구조적으로 동일하다. Compact 전후 checksum도 같으므로 죽은 ID를 제거해도 처리 결과는 바뀌지 않았다.
>
> **해석**
>
> Tombstone은 삭제 비용을 없애지 않고 순회와 Compact 비용으로 옮긴다.
>
> ### 현재 요구사항에서 도달한 설계안
>
> | 요구사항 | 담당 구조와 동작 |
> |---|---|
> | `EnemyId` 검색 | `TMap<int32, FEnemyState>::Find()` |
> | 생성 순서 순회 | `TArray<int32> CreationOrder` 순회 |
> | 추가 | Map과 Order에 같은 ID 추가 |
> | 삭제 | Map에서 즉시 제거, Order에는 Tombstone 유지 |
> | 참조 안전성 | raw pointer를 장기 저장하지 않고 ID를 다시 조회 |
> | 누적된 Tombstone | 안전한 시점이나 임계치에서 Compact |
>
> 이 설계의 비용도 사라지는 것은 아니다. 삭제 비용을 즉시 지불하지 않는 대신 Tombstone 순회 비용과 가끔 수행하는 `Compact` 비용으로 옮긴다. 중요한 점은 비용을 없앴다고 착각하지 않고, 전투 중처럼 민감한 시점에는 분산하고 웨이브 종료처럼 여유 있는 시점에 정리하도록 통제할 수 있게 됐다는 것이다.

## 복습

> [!abstract]- 30초 복습
> **한 문장으로:** 검색과 생성 순서를 분리하고, 삭제 비용은 Tombstone과 Compact로 지불 시점을 조절한다.
>
> **기억할 연결:** raw pointer는 재할당에 약하고, Index는 `RemoveAt()` 이후 낡으며, `RemoveAtSwap()`은 생성 순서를 깨뜨린다.
>
> **먼저 할 것:** 자료구조를 바꾸기 전에 중복 `Find`부터 제거한다.
>
> **숫자로 확인:** 중복 검색은 `1,999,800 → 999,900`, Compact 후 순회 검사는 `1,000,000 → 250,000`으로 줄었다.
