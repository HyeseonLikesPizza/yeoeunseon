## 문제 상황

적 정보를 ID로 자주 찾는다. 지금은 vector를 앞에서부터 검색한다.

```cpp
struct Enemy
{
    int Id;
    int HP;
};

Enemy* FindEnemy(std::vector<Enemy>& Enemies, int TargetId)
{
    for (Enemy& E : Enemies)
    {
        if (E.Id == TargetId)
            return &E;
    }
    return nullptr;
}
```

선형 검색은 O(n), unordered_map의 find는 평균 O(1)이다. 그렇다면 ID 검색이 있다는 이유만으로 hash map으로 바꿔야 할까?

- vector의 선형 검색이 더 빠를 수 있는 조건을 CPU 캐시와 연결해 설명해라.
- 자료구조를 선택할 때 탐색 복잡도 외에 무엇을 확인해야 할까?

## 비교하며 풀어간 과정

여기서는 **비교 실험 자체가 풀이**다. 조건을 바꿔 결과를 보고, 그 결과 때문에 다음 비교로 넘어갔다.

> [!question]- 1부 — 같은 개수인데도 비용이 달라지는 이유
> ### 1. 적이 적으면 vector가 무조건 빠를까?
>
> 처음에는 작은 vector가 유리할 것이라고 생각했다. 그런데 측정 조건을 바꾸자 map이 이기는 경우도 나왔다.
>
> **원소 수만으로 승자를 정할 수 없었다.** 그래서 적 8개와 조회 목록을 유지하고, 목록의 순서만 바꿨다.
>
> | 같은 8개 · 같은 성공/실패 혼합 조회 | vector | map |
> |---|---:|---:|
> | 일정한 패턴 반복 | 2.20ns | **1.27ns** |
> | 같은 목록을 섞음 | **5.37ns** | 6.44ns |
>
> 위 값은 후속 VTune 1차 수집이다. 2차에서도 승자가 같았다. 두 조건의 조회 목록은 각각 65,536개이며, 찾는 키별 횟수·성공률·비교 횟수도 같았다.
>
> **비교를 더 한 것도 아닌데 왜 느려졌을까?**
>
> VTune에서 명령 수는 거의 같았지만, 섞은 순서에서는 분기 실패와 CPI가 늘었다.
>
> CPU는 조건문의 다음 실행 경로를 예측한다. 예측이 틀리면 잘못 진행한 일을 취소하는 비용이 생긴다. 이번에는 순서를 바꾸면서 그 비용이 커지는 지표가 관찰됐다.
>
> → 작은 입력의 차이를 전부 캐시 때문이라고 설명하면 안 된다. **조회 순서와 분기 예측도 실제 비용에 영향을 줬다.** 시간 차이 중 정확히 몇 %가 분기 때문인지는 분리하지 않았다.
>
> [[실험/VectorVsHash_VTune 조회 순서 실험|조회 목록과 분기 지표]]
>

> ### 2. 같은 vector도 어디에서 찾느냐에 따라 다를까?
>
> 앞에서부터 찾는다면, 첫 원소에서 끝나는 조회와 마지막까지 가는 조회는 하는 일부터 다르다.
>
> | 4,096개 · 반복 조회 | vector 비교 수 | vector 시간 | map 시간 |
> |---|---:|---:|---:|
> | 첫 원소 찾기 | 1회 | 0.31ns | 1.09ns |
> | 마지막 원소 찾기 | 4,096회 | 약 782ns | 약 1.32ns |
>
> **첫 원소를 반복해서 찾는 조건에서는 vector가 빨랐다.**
>
> → O(n)은 매번 n개를 비교한다는 뜻이 아니다. 실제 성공률과 발견 위치를 봐야 한다. 이 극단적으로 유리한 입력을 일반 무작위 조회로 간주하지 않는다.
>
> 여기까지는 “얼마나 비교했는가”의 차이다. 그렇다면 **비교 수가 같아도 읽는 방식 때문에 비용이 달라질까?**
>
> [[실험/VectorVsHashFactors_실험 기록|발견 위치 비교 기록]]
>

> ### 3. vector는 연속 메모리인데, 배치를 바꿀 이유가 있을까?
>
> 같은 50,000개, 같은 ID·저장 순서·조회 목록을 사용하고 원소 크기만 8B → 256B로 키웠다.
>
> ```text
> 8B 원소      ID ─8B─ ID ─8B─ ID
> 256B 원소    ID ─────────256B───────── ID
> ```
>
> vector 전체는 연속이다. 하지만 찾는 데 필요한 ID 사이의 간격은 다르다. 이 간격이 stride다.
>
> **비교 수는 같은데, 큰 원소의 vector는 약 12~13배 느려졌다.** VTune에서는 L1 miss·L3 접근·메모리 대기도 늘었다.
>
> CPU는 메모리에서 cache line 단위로 데이터를 가져온다. 작은 원소라면 한 번 가져온 구간에 다음 ID도 들어올 수 있다. 원소가 크면 같은 수의 ID를 비교해도 훨씬 넓은 주소 범위를 지나간다.
>
> → **연속 저장과 필요한 값이 촘촘한 것은 다르다.** 이번에는 배치 변화와 캐시 지표·시간 변화가 함께 관찰됐다.
>
> **그럼 ID만 따로 모으면 비용이 다시 줄까?**
>
> 별도 A/B 수집에서 256B Enemy 배열 검색과 4B ID 배열 검색을 비교했다. 찾은 뒤 같은 HP를 읽도록 해 기능도 유지했다.
>
> ```text
> 256B Enemy에서 ID 검색    약 99μs / 조회
> 4B ID 배열에서 검색       약 7.9μs / 조회
>
> 비교 횟수 · 조회 결과     같음
> 실행 명령 수             오히려 증가
> cache miss · 대기         감소
> ```
>
> **덜 비교해서가 아니라, 같은 비교를 더 싸게 수행했다.** Assembly의 두 검색 루프도 scalar 비교였다. ID 분리만 SIMD가 된 결과가 아니었다.
>
> 원소 크기 비교와 ID 분리는 별도 수집이다. 배수를 합치지 않는다. ID/HP 배열 생성·유지 비용은 검색 시간에 포함하지 않았으므로 전체 시스템 적용은 따로 판단해야 한다.
>
> [[실험/VectorVsHash_VTune 큰 원소 실험|원소 크기 비교]] · [[실험/VectorVsHash_VTune ID 분리 실험|ID 분리 후 지표]]
>

> ### 4. 후보를 조금만 보는 map도 캐시 영향을 받을까?
>
> 큰 원소 실험의 map은 같은 512개 조회 목록을 반복했다. 그 조건에서 빠른 것을 보고 “map에는 캐시 비용이 없다”고 결론 낼 수는 없었다.
>
> 이번에는 같은 map에 50,000개를 넣고, 조회 목록 길이와 성공률을 고정한 뒤 **찾는 키의 범위**를 넓혔다.
>
> | 실제로 찾은 서로 다른 키 | 조회당 equality | 조회 시간 |
> |---|---:|---:|
> | 512개 | 약 1.12회 | 3.27~3.32ns |
> | 36,587개 | 약 1.12회 | 4.49~4.55ns |
>
> **후보 비교와 명령 수는 비슷했지만 약 1.37배 느려졌다.** L1 miss·L3 hit·메모리 대기도 늘었다.
>
> L1 miss는 가까운 L1에서 못 찾았다는 뜻이다. L3 hit는 못 찾았다는 뜻이 아니라, **더 아래의 L3까지 가서 찾았다**는 뜻이다.
>
> 같은 후보를 자주 다시 읽는 것과 더 많은 bucket·노드로 접근이 퍼지는 것은 다르다.
>
> → map은 비교 수를 줄이지만, **그 후보를 가져오는 비용까지 없애지는 않는다.** 평균 O(1)이 조회당 고정 시간을 뜻하지는 않는다.
>
> 넓은 키 목록도 반복한 warm 실험이다. 모든 키를 한 번씩 찾거나 cold cache를 강제한 것이 아니다. 앞선 혼합 조회와 입력도 달라 그 시간 차이 전체를 이번 배수로 설명하지 않는다.
>
> [[실험/VectorVsHash_VTune 조회 키 범위 실험|고정 조건과 캐시 지표]]

> [!question]- 2부 — 어떤 경우에 vector가 이기고, 무엇까지 비교해야 할까?
> ### 5. map의 충돌이 심하면 어떻게 될까?
>
> 같은 4,096개에서 해시만 바꿨다. 정상 해시와 모든 키가 같은 해시를 만드는 경우를 비교했다.
>
> | 조건 | map equality/조회 | map 시간 |
> |---|---:|---:|
> | 정상 해시 | 약 1.28회 | 약 1.8ns |
> | 모두 같은 해시 | 약 3,070회 | 약 6,957ns |
>
> 같은 조회의 vector는 약 3,070회 비교하며 약 589ns였다. **충돌 조건에서는 비교 수가 같아도 vector가 훨씬 빨랐다.**
>
> 생성된 코드에서 vector는 일정 간격으로 전진했고, 이번 MSVC map은 후보 노드의 링크를 따라갔다.
>
> → 여기서는 충돌로 map의 작업량이 늘었다. 또 같은 비교 수라고 접근 방식까지 같은 것은 아니었다. 노드 접근 때문에 발생한 stall의 기여율까지 측정한 것은 아니다.
>
> Load factor를 1 → 4로 높인 별도 비교에서도 equality는 약 1.28 → 3.51회로 늘고 시간이 증가했다. 낮출수록 항상 빨라진다는 규칙으로 일반화하지 않는다.
>
> [[실험/VectorVsHashFactors_실험 기록|충돌·load factor 비교]] · [[실험/VectorVsHashFactors_Assembly|실제 탐색 루프]]
>

> ### 6. 정수 ID 대신 긴 문자열을 찾으면?
>
> 이번에는 16개 문자열 키를 성공 조회했다.
>
> | 키 길이 | vector | map |
> |---|---:|---:|
> | 8자 | 24.63ns | **11.70ns** |
> | 공통 접두사를 가진 128자 | **36.61ns** | 94.26ns |
>
> **원소 수가 같아도 키가 달라지자 승자가 바뀌었다.**
>
> 문자열을 해시하거나 같은지 비교하는 데도 비용이 든다. 길이를 바꾸면 문자열 저장 방식도 함께 달라지므로 순수 해시 비용 하나로 설명하지 않는다.
>
> → “몇 개를 저장했나?”뿐 아니라 **무엇을 키로 찾나?**도 선택 조건이다.
>
> [[실험/VectorVsHashFactors_실험 기록|문자열 키 비교]]
>

> ### 7. 조회가 빨라졌으면 교체해도 될까?
>
> 같은 4,096개·8B Enemy로 조회 외의 작업도 비교했다.
>
> | 연산 | vector | map |
> |---|---:|---:|
> | 혼합 ID 조회 · 조회당 | 약 588ns | **약 1.8ns** |
> | 모든 HP 합산 · 원소당 | **0.19ns** | 2.71ns |
> | reserve 후 생성 사이클 · 입력당 | **0.74ns** | 36.44ns |
> | ID로 절반 삭제 · 삭제당 | 3,145ns | **17.16ns** |
>
> **조회의 승자와 순회·생성의 승자는 달랐다.**
>
> 적을 자주 ID로 찾는다면 map의 조회 이득이 중요하다. 반대로 전체를 갱신하는 일이 대부분이라면 순회 비용도 중요하다.
>
> → 선택 기준은 **각 연산의 비용 × 실제 호출 빈도**다. 검색 하나의 배수로 전체 시스템의 성능을 정하지 않는다.
>
> 생성 사이클은 할당·추가·합산·소멸 전체다. 삭제는 vector에서 검색 후 순서를 유지하며 erase했고, map에서는 키로 erase했다. map은 vector의 순서 요구사항을 대신 보장하지 않는다. HP 합산 역시 실제 게임의 전체 갱신은 아니다.
>
> [[실험/VectorVsHashFactors_실험 기록|생성·순회·삭제의 조건]]

## 결론

> [!success] 적게 비교하는 것과 싸게 읽는 것은 다르다
> vector는 여러 번 비교해도 데이터를 싸게 읽으면 이길 수 있다.
> map은 검색 범위를 줄이지만 해시·후보 접근 비용은 남는다.

이번에는 앞 원소 반복 조회, 일부 작은 입력, 심한 해시 충돌, 일부 긴 문자열 조건에서 vector가 이겼다. **작은 입력에서도 map이 이겼고, 정상 해시의 큰 무작위 조회에서는 map이 빨랐다.**

따라서 “몇 개 이하면 vector”를 외우는 대신 다음을 구분한다.

| 확인할 것 | 이번 실험에서 연결한 것 |
|---|---|
| 얼마나 비교하나? | 발견 위치 · hash collision |
| 같은 비교가 왜 더 비싸지? | ID 간격 · cache miss · 메모리 대기 |
| 캐시 외의 이유는 없나? | 조회 순서 · 분기 실패 |
| 개선이 정말 작동하나? | ID 분리 뒤 같은 결과, miss·시간 감소 |
| 실제 시스템에도 유리한가? | 조회 + 순회 + 생성·삭제 + 유지 비용 |

**측정한 것은 시간과 지표가 함께 변했다는 사실이다.** cache/TLB별 기여율, DRAM bandwidth 포화까지 증명한 것은 아니다. 주소 배치만 보고 모든 차이를 캐시 탓으로 묶지 않는다.

### 이름만 보고 떠올릴 것

```text
Equality      → 실제 후보 비교 수
Stride        → 다음 필요한 값까지의 주소 간격
Locality      → 가까운 데이터 / 방금 쓴 데이터 재사용
Cache miss    → 가까운 캐시에 없음
L3 hit        → 더 아래의 L3에서 찾음
Instructions  → 실행한 명령 수
CPI           → 명령당 cycle
Branch miss   → 실행 경로 예측 실패
```

> [!note]- 상세 조건·코드·원본 기록
> Windows MSVC 최적화 빌드의 std::vector / std::unordered_map 비교다. Unreal TArray/TMap이나 실제 게임 프레임 측정은 아니다. 내부 링크 탐색 설명은 확인한 MSVC 구현에 한정한다.
>
> 기본 비교는 각각 134조건 × 7 samples로 두 번 실행했고, 중간 확인 실행도 추가했다. 조회 규모 비교에는 3개 seed를 사용했다. 본문의 기본 비교 수치는 최종 Run 1 중앙값의 대표 예다.
>
> 이후 조회 목록 8조건, 순서·키 범위 41조건, 고정 기준 대조 12조건도 각각 두 번 실행했다. 검사한 checksum·완료 후 크기 불일치는 0이었다.
>
> 후속 VTune 수집은 조회 순서 8회, 원소 크기 8회, ID 분리 4회, map 키 범위 4회다. 해당 단계에는 이 수집의 대표값을 사용했다. 입력·빌드·코어 고정 조건이 다른 실험의 절대 시간과 배수를 합치지 않는다. hardware event는 sampling 추정치이며, 지표의 0이 실제 발생 0을 보장하지 않는다.
>
> 초기에는 조회 목록 길이와 짧은 측정 구간에 따라 승자가 달라졌다. 확장 코드에서는 구현별로 약 2ms/sample을 목표로 반복 수를 조정했다. 이후 목록 길이·순서·키 범위를 나눠 확인했다.
>
