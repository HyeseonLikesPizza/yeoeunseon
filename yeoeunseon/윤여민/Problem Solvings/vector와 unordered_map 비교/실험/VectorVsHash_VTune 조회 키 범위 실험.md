## 같은 map도 찾는 키가 넓어지면 느려질까?

**같은 map도 늘 찾던 적만 찾을 때와 여러 적을 골고루 찾을 때의 비용은 달랐다.**

```text
저장된 적: 양쪽 모두 50,000명
조회 횟수: 양쪽 모두 한 목록당 65,536번

512개의 ID만 반복해서 찾기       약 3.3ns / 조회
더 넓은 ID 범위에서 골라 찾기    약 4.5ns / 조회
```

조회당 ID 비교는 양쪽 모두 약 1.12회였다. **더 많이 비교해서가 아니라, 비슷한 수의 후보를 읽는 데 더 많은 비용이 든 것이다.**

앞선 큰 원소 실험의 map은 같은 512개 조회 목록을 반복했다. 그래서 “map은 메모리 배치에 영향을 받지 않는다”로 일반화하지 않고, 조회 범위만 따로 확인했다.

## 무엇을 고정했나?

| 고정 조건 | 값 |
|---|---|
| map | Enemy 50,000개, 원소 8B, 동일한 ID·HP·삽입 순서 |
| 해시·bucket | `std::hash<int>`, bucket 65,536개, load factor 약 0.763 |
| 조회 목록 | 65,536개 정수, 모두 성공 조회, 같은 seed |
| 실행 | warm-up 후 5초 반복, benchmark Thread만 logical CPU 0에 고정 |

키 후보를 **512개 / 50,000개**로 바꿨다. 좁은 후보도 map 전체에 걸쳐 고르게 배치했으며, 앞의 512개만 찾도록 만들지 않았다.

```text
좁은 후보 → 실제로 찾은 서로 다른 키 512개
넓은 후보 → 실제로 찾은 서로 다른 키 36,587개
```

50,000개 후보에서 무작위로 65,536번 뽑았으므로 모든 키를 한 번씩 찾은 것은 아니다. 목록 길이와 성공률은 같지만 키별 빈도·접근 순서·bucket과 노드의 재접근 범위는 달라진다. 따라서 순수 캐시 효과 하나만 바꾼 실험으로 부르지는 않는다.

2026-10-11, Intel Core i5-14600KF / MSVC `/O2 /Zi /EHsc /std:c++17` / VTune 2026.4.

```text
512 → 50,000 → 50,000 → 512
각 조건 별도 process, 각 5초
```

## 더 많이 비교한 결과일까?

| 조회 키 후보 | 1차 · ns/조회 | 2차 · ns/조회 | equality/조회 |
|---|---:|---:|---:|
| 512개 | 3.319 | 3.274 | 1.1214 |
| 50,000개 | 4.548 | 4.493 | 1.1157 |

**두 번 모두 약 1.37배 느려졌다. 넓은 조건에서 equality가 늘어난 것은 아니다.**

equality는 측정 밖에서 동일한 키·삽입 순서·bucket 정책의 진단 map으로 셌다. 시간과 hardware event는 계측 없는 원래 map을 사용했다.

모든 capture에서 기대한 HP 합과 실제 결과의 불일치는 0이었다. 좁은 목록의 checksum은 35,818,544, 넓은 목록은 35,852,573이다. 찾는 키가 다르므로 두 조건의 합까지 같아야 하는 실험은 아니다.

## CPU에서는 무엇이 달라졌나?

| 조회당 추정치 | 512개 · 1차 / 2차 | 50,000개 · 1차 / 2차 |
|---|---:|---:|
| 실행 명령 수 | 35.79 / 35.77 | 35.76 / 35.75 |
| cycle | 16.55 / 16.35 | 22.34 / 22.32 |
| 분기 실패 | 0.123 / 0.121 | 0.096 / 0.107 |
| L1 miss | 0.631 / 0.609 | 1.483 / 1.518 |
| L2 hit | 0.631 / 0.614 | 0.948 / 0.978 |
| L3 hit | 0 / 0 | 0.546 / 0.537 |
| L1 miss 관련 stall cycle | 0.548 / 0.519 | 5.973 / 6.019 |
| CPI | 0.462 / 0.457 | 0.625 / 0.624 |

평균 주파수는 약 5.28GHz로 비슷했고, 대상 모듈의 E-core cycle은 모두 0이었다. `find`가 별도 함수로 실행돼 `MapLookup`의 self time만 보지 않고 실행 파일 모듈 전체를 집계했다. 준비·출력 비용도 포함되지만 5초 반복 검색이 대부분이다.

**명령 수와 후보 비교는 거의 같은데, 더 먼 캐시에서 데이터를 가져오는 횟수와 대기가 늘었다. 분기 실패 증가로 설명되는 결과도 아니다.**

표를 읽으면 다음처럼 이어진다.

- **equality·명령 수가 비슷함:** 더 많은 후보를 비교하거나 더 많은 명령을 실행해서 느려졌다는 설명은 맞지 않는다.
- **L1 miss·L3 hit 증가:** 가까운 L1에서 못 찾고 더 아래 캐시에서 가져오는 경우가 늘었다. L3 hit는 못 찾았다는 뜻이 아니라 **L3까지 가서 찾았다**는 뜻이다.
- **stall·CPI 증가:** 명령 개수는 비슷한데 데이터를 기다리는 cycle이 늘면서 명령당 cycle도 커졌다.

좁은 범위에서는 같은 bucket과 후보 노드를 자주 다시 읽는다. 넓은 범위에서는 더 많은 bucket과 노드로 접근이 퍼진다. **이 재사용 차이가 캐시 지표와 시간 차이를 설명한다.** 노드마다 정확히 어느 캐시에 있었는지 추적하거나 차이의 전부를 캐시 하나에 배분한 것은 아니다.

→ 평균 O(1)은 조회당 시간이 고정된다는 뜻이 아니다. 후보가 적어도 **그 후보를 어디서 가져오는지**에 따라 실제 시간은 달라진다.

L3 miss는 약 0.0015 / 0으로 낮게 보고됐다. 이것을 “RAM 접근은 전혀 없었다”로 해석하지 않는다. 이번 결과는 DRAM bandwidth 한계보다 가까운 캐시에서 처리할 수 있는 비율이 달라지는 설명과 맞는다. 캐시별 기여율이나 대역폭 포화를 증명한 것은 아니다.

## 어디까지 적용할 수 있나?

**좁은 키 반복으로 얻은 map 시간을 모든 조회 패턴의 대표값으로 쓰면 안 된다.**

다만 앞선 512개 혼합 목록과 이번 65,536개 성공 목록은 입력·성공률·키 생성 방식이 다르다. 이번 1.37배를 앞선 실험의 시간 차이 전체에 소급 적용하지 않는다. 차가운 캐시를 강제로 만든 실험도 아니며, 넓은 목록도 계속 반복했다.

노드마다 고정 비용이 있다거나 모든 map이 이 배수로 느려진다는 결론은 아니다. 이번 MSVC 구현에서 **비슷한 후보 수라도 재접근 범위가 넓어지면 실제 조회 비용이 커질 수 있음**을 확인했다.

hardware event는 multiplex sampling 추정치다. summary MUX Reliability는 약 0.968~0.997이었다. 0은 실제 발생 0의 보장이 아니며, stall cycle을 더해 원인별 시간으로 나누지 않는다. [Intel — Multiplex Events](https://www.intel.com/content/www/us/en/docs/vtune-profiler/user-guide/2025-1/allow-multiple-runs-or-multiplex-events.html)
