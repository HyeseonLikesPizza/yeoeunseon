## 실행 조건

2026-10-10 · Windows · MSVC 19.44.35228 · x64 /O2 /std:c++17 · hardware_concurrency()=20.

CPU 모델·캐시 용량·주파수는 확인하지 않았다. Thread affinity를 고정하지 않았고, 다른 프로세스와의 간섭을 완전히 제거한 실행도 아니다.

- 단일 Thread에서 표준 vector / unordered_map을 비교.
- 기본 map은 실제 std::hash<int> 사용. 충돌/고비용 해시는 별도 template.
- 양쪽에 같은 데이터·저장 순서·조회 목록 사용.
- 정수 키는 유일한 양수, 실패 조회는 존재하지 않는 음수.
- 컨테이너·조회 목록 생성은 lookup 측정 밖.
- 사전 실행 후 7 samples, 실행 순서 교대, 중앙값 사용.
- 구현마다 반복 횟수를 별도 보정해 약 2ms/sample 목표. 한 pass의 입력은 같지만 전체 반복 횟수는 다를 수 있다.
- noinline 함수, checksum 소비, 반복 경계 compiler fence로 계산 제거/반복 이동을 억제.
- equality 카운터는 별도 진단 map에서 측정. 성능을 잰 map에 카운터를 넣지 않았다.
- 원시 기록에 min/max, 반복 횟수, bucket 수, load factor, 비교 횟수를 남겼다.

이는 **반복해서 데워진 workload의 평균 처리 비용**이다. 개별 lookup의 cold latency나 프레임 전체 시간은 아니다. 매우 짧은 연산은 timer·호출·누적 비용의 영향을 받고, warm-up과 보정이 있어도 모든 잡음을 없애지는 못한다.

기본 조회 목록은 4,096개이며 N≥16,384에서는 512개다. 큰 map도 **그 목록에 등장하는 일부 키를 계속 재조회**한다. map 전체가 매번 cache에 들어온다는 의미가 아니며, 50,000개 전체 키를 새 순서로 조회하는 workload의 성능으로 사용하지 않는다.

전체 비교의 두 독립 기록은 각각 134조건이다. 그 뒤 큰 입력의 조회 목록 후속 실험 8조건을 두 번 더 실행했다. 기록된 checksum/삭제 후 크기 검사는 모두 통과했다. checksum 일치만으로 임의의 프로그램 전체 정확성을 증명하는 것은 아니다.

이후 목록 크기를 고정해 조회 순서와 접근하는 키 범위를 나눠 봤다. 41조건과 기준 대조 12조건을 각각 두 번 더 실행했다. [[VectorVsHashPatterns_실험 기록|후속 실험과 결과의 의미]]에 따로 기록했다.

## 결과를 어떻게 읽는가

아래는 Run 1 대표값이다. lookup은 **ns/조회**, scan은 **ns/원소**다.

### 원소 수와 실제 비교량

4,096개 혼합 조회에서 vector는 평균 약 3,070번 비교했고 기본 map은 equality 약 1.28번 수행했다.

→ 많은 무작위 ID 조회에서는 연속 저장의 장점만으로 수천 번의 추가 비교를 상쇄하지 못했다. “vector도 캐시에 들어가면 map보다 빠르다”로 일반화할 수 없다.

반대로 첫 원소 반복 조회는 1번 비교로 끝났다.

→ Big-O의 최악/평균 표현과 실제 찾은 위치를 구분한다.

### 작은 입력에서 결과가 뒤집힌 후속 실험

| N=8 · 조회 목록 길이 | 성공 vector/map | 실패 vector/map | 혼합 vector/map |
|---|---:|---:|---:|
| 4,096 | 4.71 / 2.39 | 1.72 / 1.61 | 4.07 / 1.73 |
| 262,144 | 6.67 / 7.21 | 1.74 / 7.19 | 4.89 / 7.31 |

같은 실행의 조회 목록 후속 실험에서 가져온 값이다. 정확한 배수보다 조건 변경에 따른 방향을 본다.

조회 목록은 약 16KiB → 1MiB다. map equality와 vector 비교 횟수는 거의 같았지만 시간이 달라졌다.

→ 조회 목록 크기·분기 패턴 반복 등 **실행 환경의 영향이 존재한다.** Branch Miss와 캐시 지표를 수집하지 않았으므로 둘 중 하나를 단독 원인으로 확정하지 않는다.

### 큰 입력에서도 조회 목록이 영향을 주는가?

50,000개 map의 약 2ns 조회는 512개 목록을 반복한 조건이었다. 같은 N에서 목록을 늘려 확인했다.

| 성공 조회 · N=50,000 | vector ns | map ns | map의 Run 2 ns |
|---|---:|---:|---:|
| 조회 목록 512개 | 4,810 | 2.25 | 2.25 |
| 조회 목록 65,536개 | 4,759 | 9.43 | 9.42 |

map equality는 약 1.32 → 1.38회로 소폭 증가한 반면 시간은 약 4배 늘었다. 혼합 조회도 map 약 2.00 → 10.14ns였고 두 번째 실행에서 반복됐다.

→ 많은 키를 찾게 하고 조회 목록도 키우면, 짧은 목록 반복 결과와 달라진다. 그래도 여전히 warm workload다. query 배열의 접근, 후보 노드의 접근 범위, 분기 예측이 함께 달라지므로 이 차이를 단독으로 cache miss에 귀속하지 않는다. 여전히 큰 무작위 조회에서는 map이 vector보다 빨랐다.

[[VectorVsHashCoverage_Run1.txt|후속 Run 1]] · [[VectorVsHashCoverage_Run2.txt|후속 Run 2]]

### 원소 크기와 ID 분리

| N=4,096 · 혼합 | vector | map | vector 비교 횟수 |
|---|---:|---:|---:|
| 8B | 587 | 1.67 | 약 3,070 |
| 64B | 740 | 1.89 | 약 3,070 |
| 256B | 1,196 | 2.00 | 약 3,070 |

**같은 비교 횟수인데 vector의 비용이 증가했다.**

그 다음 검색용 ID만 분리했다.

| ID 분리 후속 | 256B 원소 검색 | 4B ID 검색 | 독립 Run 2 배수 |
|---|---:|---:|---:|
| 4,096개 | 1,223 | 602 | 약 2.03x |
| 50,000개 | 84,852 | 7,304 | 약 11.63x |

두 방식은 같은 키 순서·조회 결과를 유지했다. ID 배열에서 찾으면 해당 Index의 HP를 읽었다. 검색 복잡도는 여전히 선형이다.

→ 비교 횟수 감소 없이 **접근 배치를 개선한 효과**가 확인됐다. 실제 생성 루프는 scalar이며 stride는 256B/4B였다. 루프 제어 방식도 완전히 같은 기계어는 아니므로 시간 차이 전부를 특정 cache level의 miss로 환산하지 않는다.

### 충돌과 load factor

| 4,096개 혼합 조회 | map ns | equality/조회 |
|---|---:|---:|
| 기본 해시 · load 1 | 1.84 | 1.28 |
| 모든 hash=0 | 6,957 | 3,069.81 |

충돌 map과 vector는 이 입력에서 평균 키 비교 횟수가 같았다. vector는 약 589ns였다.

→ 후보 수 폭증은 확인했다. 같은 후보 수라도 노드 링크를 읽는 map과 일정 간격으로 전진하는 vector의 실행 비용은 다르다. 메모리 대기와 분기 비용의 기여율은 아직 모른다.

| load factor | bucket 수 | 최대 bucket 크기 | equality/조회 | map ns |
|---|---:|---:|---:|---:|
| 0.25 | 16,384 | 4 | 0.70 | 1.61 |
| 1 | 4,096 | 6 | 1.28 | 1.73 |
| 4 | 1,024 | 10 | 3.51 | 9.80 |

→ bucket을 줄이면 후보 비교가 늘 수 있다. 반면 bucket을 무조건 늘리는 최적값은 여기서 정하지 않았다. 공간과 cache 비용도 함께 변한다.

### 해시 작업과 문자열

12회 mixing을 추가한 map은 4,096개에서 약 16.92ns였다. 기본 해시보다 equality는 조금 적었지만 시간은 길었다.

→ 후보 수뿐 아니라 **hash 함수 자체의 연산**도 비용이다. mixing은 hash 값과 bucket 분포도 바꾸므로 순수 hash 계산 시간만 분리한 실험은 아니다.

16개 문자열 조회에서는 8자 키의 map이 빨랐고, 128자 키에서는 vector가 빨랐다.

→ 문자열 길이에 따라 해시·비교·inline/heap 저장이 함께 달라진다. 키는 공통 접두사를 갖고 끝부분에서 달라지는 인위적인 조건이다. 모든 긴 문자열에 같은 승패를 기대하지 않는다.

### 전체 순회·생성·삭제

4,096개 8B 원소의 HP 합산은 vector 0.19ns/원소, map 2.71ns/원소였다.

→ ID lookup의 승자가 순회의 승자는 아니다. 이번에 본 vector 합산 루프도 scalar였다. 실제 상태 갱신·복잡한 함수 호출은 이 합산과 다를 수 있다.

reserve 후 생성 사이클은 vector 약 0.74ns/입력, map 약 36.44ns/입력이었다.

→ 생성 시 할당 방식도 선택 비용이다. 이 수치는 생성·추가·합산·소멸을 모두 포함한다. 순수 allocation 횟수와 삽입 시간은 따로 계측하지 않았다.

ID로 절반 삭제했을 때 50,000개에서는 vector 약 40,748ns/삭제, map 약 36.50ns/삭제였다.

→ vector는 대상 검색과 뒤 원소 이동을 반복했다. map의 순서 보장은 다르므로 같은 게임 요구사항을 만족하는지 별도 판단한다. vector의 erase/remove 일괄 삭제나 swap 삭제와 비교한 결과는 아니다.

## 재현

`.obsidian`과 `tmp`가 있는 학습 폴더에서 PowerShell로 실행한다. 소스는 이 문서와 같은 `실험` 폴더에 있고, 빌드 생성물은 Git에서 제외한 `tmp`에 둔다.

```powershell
& '.\윤여민\Problem Solvings\vector와 unordered_map 비교\실험\재현\BuildVectorFactors.cmd'
.\tmp\VectorVsHashFactors.exe
.\tmp\VectorVsHashFactors.exe coverage
```

다른 컴파일러에서는 MSVC 전용 noinline 표기를 바꿔야 한다. Debug 빌드나 다른 STL 결과를 지금 값과 섞지 않는다.

프로파일링 전용 실행은 같은 혼합 조회를 정해진 초 동안 반복한다.

```bat
tmp\VectorVsHashFactors.exe profile vector 8 50000 10
tmp\VectorVsHashFactors.exe profile vector 256 50000 10
tmp\VectorVsHashFactors.exe profile map 8 50000 10
```

전체 benchmark 실행이 아니라 위처럼 한 workload를 수집하고 VectorLookup/MapLookup 함수에 필터를 건다. 시간 제한 동안의 반복 수가 다를 수 있으므로 hardware event 총량을 비교할 때는 조회 수나 명령 수로 정규화한다.

### VTune 수집 실패와 남은 확인

```text
vtune -collect uarch-exploration -result-dir <새 결과 폴더>
      -- VectorVsHashFactors.exe profile vector 8 50000 5

Cannot enable Hardware Event-Based Sampling or Hardware Tracing.
Sampling Driver / administrator 확인 요청
```

당시 일반 실행과 권한 요청 실행 모두 같은 오류였다. 이후 확인해 보니 샌드박스 밖 실행은 Windows 관리자 실행이 아니었다. 드라이버는 이미 실행 중이었고, UAC를 거쳐 실제 관리자 권한으로 실행하자 3초 하드웨어 수집이 성공했다. 드라이버 설치·시스템 설정 변경은 수행하지 않았다. [[VTune 하드웨어 수집 권한 문제 해결|해결 기록]]

수집 기능 확인과 별개로, 다음 A/B 분석은 아직 남아 있다:

작은 입력의 같은 목록을 섞는 조건은 이후 [[VectorVsHash_VTune 조회 순서 실험|8회 하드웨어 수집]]으로 확인했다. 분기 실패와 CPI가 함께 증가했다. 큰 원소 8B/256B도 [[VectorVsHash_VTune 큰 원소 실험|별도 수집]]해 cache miss·메모리 대기 증가를 확인했고, [[VectorVsHash_VTune ID 분리 실험|ID 분리 후 감소]]도 확인했다. 목록 길이·충돌 조건은 추가 분석 대상이다.

- 작은 입력의 목록 길이 실험: Branch Miss·cache 관련 지표.
- 넓은 조회 키 범위: map의 반복 키 재사용 효과와 cache/TLB 비용을 확인. bandwidth 한계는 별도로 검증.
- 충돌 map: 후보 링크 탐색의 실행 시간과 메모리 대기.
- 동일 조건의 반복 capture, 실행 순서 교대, 주파수/스케줄링 차이 확인.

Back-End Bound만으로 cache miss를 확정하지 않는다. 지표가 모자라면 **현재 확인한 것은 어디까지인지** 유지하고 다음 실험을 정한다.
